# 260729 TIL - Spring AI (ChatClient, Advisor, ChatMemory)

## 오늘 배운 내용 한눈에 보기

오늘은 Spring AI를 이용해서 **AI 챗봇 서버**를 만드는 방법을 배웠습니다. 핵심 흐름은 다음과 같습니다.

```
사용자 입력 (JSP form)
   ↓
Controller (MainController)
   ↓
Service (ChatService, ChatService2) - ChatClient 사용
   ↓
ChatClient - 프롬프트 작성 + Advisor 체인 + AI 모델 호출
   ↓
ChatModel (Groq의 openai/gpt-oss-120b 모델)
   ↓
응답을 다시 화면에 렌더링 (redirect + flash attribute)
```

프로젝트는 `spring-ai-starter-model-openai` 의존성을 사용하지만, 실제로는 `spring.ai.openai.base-url`을 Groq 주소로 바꿔서 **OpenAI 호환 API를 제공하는 Groq**를 호출하고 있습니다. (OpenAI 스펙만 맞으면 다른 회사 모델도 그대로 쓸 수 있다는 뜻입니다.)

---

## 1. ChatModel vs ChatClient

| 구분 | 설명 |
|---|---|
| `ChatModel` | AI 모델을 직접 호출하는 가장 저수준(low-level) 인터페이스. `chatModel.call("질문")` 처럼 단순 호출만 가능 |
| `ChatClient` | `ChatModel`을 감싸서 프롬프트 조립, 파라미터 치환, 구조화된 응답 변환, Advisor 체인 등 **편의 기능을 얹어주는 상위 API** |

실무에서는 거의 항상 `ChatClient`를 사용합니다. `ChatClient.builder(chatModel).build()` 형태로 만듭니다.

```java
public ChatService(ChatModel chatModel) {
    this.chatModel = chatModel;
    this.chatClient = ChatClient.builder(chatModel).build();
}
```

> **알게 된 점**: `ChatModel`은 자동으로 스프링 빈으로 등록되지만(`spring-ai-starter-model-openai` 의존성 덕분), `ChatClient`는 직접 `builder()`로 만들어줘야 합니다.

## 2. 프롬프트 작성하기 - `PromptTemplate`과 `chatClient.prompt()`

### 2-1. 예전 방식 (`PromptTemplate` 직접 사용, 주석 처리됨)

```java
PromptTemplate promptTemplate = new PromptTemplate("<질문>{message}</질문> ...");
chatModel.call(promptTemplate.create(Map.of("message", dto.message())))
        .getResult().getOutput().getText();
```

`{message}` 처럼 중괄호로 placeholder를 만들고, `Map.of(키, 값)`으로 실제 값을 채워 넣는 방식입니다. 이 방식은 `chatModel`을 직접 다뤄야 해서 결과를 꺼내는 코드(`getResult().getOutput().getText()`)가 길어집니다.

### 2-2. 실제로 사용한 방식 (`chatClient.prompt()`)

```java
String template = "<메시지>{message}</메시지>와 관련된 {category}을 5종 추천해줘. 가능한 한글로.";
return chatClient.prompt()
        .user(u -> u.text(template)
                .param("message", dto.message())
                .param("category", "디지몬"))
        .call().content();
```

- `.prompt()` : 새로운 프롬프트 빌더 시작
- `.user(...)` : 사용자 메시지 작성. 람다 안에서 `.text()`로 템플릿, `.param()`으로 `{key}` 값을 하나씩 채웁니다.
- `.call()` : 실제 AI 호출 실행
- `.content()` : 응답 텍스트만 String으로 꺼내기

> **문제 → 시도 → 해결**: 처음에는 `%s.formatted()`로 문자열을 직접 조립하려 했지만, 이렇게 하면 사용자 입력이 프롬프트 구조를 깨뜨릴 수 있습니다(프롬프트 인젝션 위험). `{message}` + `.param()` 방식을 쓰면 값이 안전하게 치환되고, 재사용 가능한 템플릿을 만들 수 있어서 이 방식으로 정리했습니다.

## 3. 구조화된 응답 받기 (Structured Output)

AI가 순수 텍스트가 아니라 **Java 객체 형태**로 답하게 만드는 방법을 4가지로 비교해봤습니다.

### 3-1. `.entity(Class)` - DTO 하나로 받기 (가장 간단)

```java
public record FoodDTO(String name, int price, String country, String reason) {}

public FoodDTO recommendFood(ChatDTO dto) {
    return chatClient.prompt()
            .user(u -> u.text("{message}에 관련된 음식을 추천해줘")
                    .param("message", dto.message()))
            .call().entity(FoodDTO.class);
}
```

Spring AI가 내부적으로 `FoodDTO`의 필드 구조를 AI에게 알려주는 지시문을 자동으로 추가하고, 돌아온 JSON을 파싱해서 `FoodDTO` 객체로 변환해줍니다.

### 3-2. `.entity(ListOutputConverter)` - 리스트로 받기

```java
public List<String> recommendFood2(ChatDTO dto) {
    return chatClient.prompt()
            .user(u -> u.text("{message}에 관련된 음식을 10개 추천해줘")
                    .param("message", dto.message()))
            .call().entity(new ListOutputConverter(new DefaultConversionService()));
}
```

간단한 문자열 목록만 필요할 때 사용합니다.

### 3-3. `.entity(ParameterizedTypeReference<>)` - 제네릭 타입으로 받기

```java
public Map<String, Object> recommendFood3(ChatDTO dto) {
    return chatClient.prompt()
            .user(u -> u.text("{message}에 관련된 음식을 10개 추천해줘")
                    .param("message", dto.message()))
            .call().entity(new ParameterizedTypeReference<>() {});
}
```

`Map<String, Object>`처럼 제네릭이 섞인 복잡한 타입을 받을 때, 타입 정보가 런타임에 지워지지(erasure) 않도록 `ParameterizedTypeReference`로 감싸줍니다.

### 3-4. `BeanOutputConverter` - 수동 변환 (내부 동작 이해용)

```java
public FoodDTO manual(ChatDTO dto) {
    BeanOutputConverter<FoodDTO> converter = new BeanOutputConverter<>(FoodDTO.class);
    String formatInstruction = converter.getFormat(); // AI에게 줄 "이 형식으로 답해" 지시문

    String rawResult = chatClient.prompt()
            .user(u -> u.text("{message}에 관련된 음식을 추천해줘.\n${format}")
                    .param("message", dto.message())
                    .param("format", formatInstruction))
            .call().content(); // 아직 순수 텍스트(JSON 문자열)

    return converter.convert(rawResult); // 직접 파싱해서 객체로 변환
}
```

> **알게 된 점**: `.entity(FoodDTO.class)`는 사실 `BeanOutputConverter`를 내부적으로 자동으로 해주는 것입니다. `manual()` 메서드처럼 직접 풀어보니 "AI에게 포맷을 알려주는 지시문 추가 → JSON으로 응답 받기 → 파싱"이라는 3단계가 눈에 보였습니다.

## 4. Advisor - 요청/응답 가로채기

Advisor는 **AOP(관점 지향 프로그래밍)와 비슷한 개념**으로, `ChatClient`가 AI를 호출하기 전/후에 로직을 끼워 넣는 인터셉터입니다.

### 4-1. 기본 제공 Advisor: `SimpleLoggerAdvisor`

```java
.advisors(new SimpleLoggerAdvisor(), new TimingLoggerAdvisor())
```

요청/응답을 로그로 남겨주는 Spring AI 기본 제공 Advisor입니다.

### 4-2. 직접 만든 Advisor: `TimingLoggerAdvisor`

```java
public class TimingLoggerAdvisor implements CallAdvisor {

    @Override
    public ChatClientResponse adviseCall(ChatClientRequest request, CallAdvisorChain chain) {
        long startTime = System.currentTimeMillis();
        log.info("[TimingLoggerAdvisor] 시작 : prompt: {}", request.prompt().getContents());

        ChatClientResponse response = chain.nextCall(request); // 다음 Advisor(또는 실제 AI 호출)로 넘기기

        long endTime = System.currentTimeMillis();
        log.info("[TimingLoggerAdvisor] 종료 : {} ms", endTime - startTime);
        return response;
    }

    @Override
    public String getName() { return "TimingLoggerAdvisor"; }

    @Override
    public int getOrder() { return 0; } // 값이 작을수록 체인의 바깥쪽(먼저 실행)
}
```

- `chain.nextCall(request)`를 호출해야 다음 단계(다른 Advisor 또는 실제 AI 호출)로 진행됩니다. 이걸 생략하면 실제 AI 호출 자체가 일어나지 않습니다.
- `getOrder()`로 여러 Advisor 사이의 실행 순서를 조정할 수 있습니다.

> **문제 → 시도 → 해결**: 처음엔 `chain.nextCall()`을 빼먹으면 무슨 일이 일어나는지 직접 실험해봤습니다. 결과적으로 AI 호출 자체가 진행되지 않는다는 것을 확인했고, Advisor는 "중간에 끼어들되 반드시 다음 단계로 넘겨줘야 하는 구조"라는 걸 이해했습니다.

## 5. ChatMemory - AI와의 대화 기억시키기

기본적으로 AI 모델은 이전 대화를 기억하지 못합니다(매번 새로운 질문). `ChatMemory`는 대화 내역을 저장했다가 다음 질문을 보낼 때 함께 넣어주는 기능입니다.

### 5-1. 핵심 구조

```
ChatMemory (몇 개까지 기억할지 등 정책 담당)
   ↓ 내부적으로 사용
ChatMemoryRepository (실제 저장소 - 어디에 저장할지)
   ↓ 구현체
- InMemoryChatMemoryRepository (메모리, 서버 재시작하면 사라짐)
- MyBatisChatMemoryRepository (직접 구현, MyBatis로 DB 저장)
- JpaChatMemoryRepository (직접 구현, JPA로 DB 저장)
```

### 5-2. `MessageWindowChatMemory` - 최근 N개만 기억

```java
private ChatMemory messageWindow(ChatMemoryRepository chatMemoryRepository) {
    return MessageWindowChatMemory.builder()
            .chatMemoryRepository(chatMemoryRepository)
            .maxMessages(3) // 최근 3개 메시지만 유지
            .build();
}
```

전체 대화를 다 기억하면 AI에게 보내는 토큰(비용)이 계속 늘어나므로, "최근 N개만" 유지하는 정책을 사용합니다.

### 5-3. 저장소 3가지를 직접 구현 - `ChatMemoryRepository` 인터페이스

`ChatMemoryRepository`는 스프링 AI가 제공하는 인터페이스이고, 우리는 이걸 각각 다른 방식(In-memory / MyBatis / JPA)으로 직접 구현했습니다.

```java
public interface ChatMemoryRepository {
    List<String> findConversationIds();
    List<Message> findByConversationId(String conversationId);
    void saveAll(String conversationId, List<Message> messages);
    void deleteByConversationId(String conversationId);
}
```

JPA 버전 예시:

```java
public class JpaChatMemoryRepository implements ChatMemoryRepository {
    private final ChatMemoryJpaRepository repository;

    @Override
    public List<Message> findByConversationId(String conversationId) {
        return repository.findAllByConversationId(conversationId)
                .stream()
                .map(ChatMessageJPA::toMessage) // Entity -> Spring AI Message로 변환
                .toList();
    }

    @Override
    public void saveAll(String conversationId, List<Message> messages) {
        repository.deleteAllByConversationId(conversationId); // 기존 것 지우고
        // ... 새로 저장
    }
}
```

- `Message`는 Spring AI가 제공하는 타입(`UserMessage`, `AssistantMessage`, `SystemMessage`)이고, DB에는 우리가 만든 Entity(`ChatMessageJPA`, `ChatMessageMyBatis`)로 저장합니다.
- 그래서 `toMessage()` / `fromMessage()` 라는 **양방향 변환 메서드**가 각 Entity에 들어 있습니다.

```java
public Message toMessage() {
    MessageType messageType = MessageType.valueOf(this.messageType);
    return switch (messageType) {
        case USER -> new UserMessage(this.content);
        case ASSISTANT -> new AssistantMessage(this.content);
        case SYSTEM -> new SystemMessage(this.content);
        default -> throw new IllegalArgumentException("지원하지 않는 메시지 타입: %s".formatted(messageType));
    };
}
```

> **알게 된 점**: `ChatMemoryRepository`는 저장 "방식"을 결정하는 인터페이스일 뿐이고, 실제로 몇 개까지 기억할지 같은 "정책"은 `MessageWindowChatMemory`(ChatMemory 구현체)가 담당합니다. 즉, **저장소(어디에)와 정책(몇 개를)이 역할 분리**되어 있는 구조입니다.

### 5-4. 여러 개의 `ChatClient`를 빈으로 등록하고 `@Qualifier`로 골라 쓰기

```java
@Bean
public ChatClient inMemoryChatClient(ChatModel chatModel,
        @Qualifier("inMemoryChatMemory") ChatMemory memory) {
    return chatClientWith(chatModel, memory);
}

@Bean
public ChatClient jpaChatClient(ChatModel chatModel,
        @Qualifier("jpaChatMemory") ChatMemory memory) {
    return chatClientWith(chatModel, memory);
}
```

같은 타입(`ChatClient`, `ChatMemory`)의 빈이 여러 개 등록될 때는 스프링이 어떤 빈을 주입할지 알 수 없으므로 `@Qualifier("빈이름")`으로 명시해야 합니다. 사용하는 쪽에서는 이렇게 골라 씁니다.

```java
@Service
@RequiredArgsConstructor
public class ChatService2 {
    @Qualifier("jpaChatClient")
    private final ChatClient chatClient;
    ...
}
```

> **알게 된 점**: `@RequiredArgsConstructor`(롬복)가 만들어주는 생성자는 원래 `@Qualifier`를 생성자 파라미터로 그대로 옮겨주지 않습니다. `lombok.config`에 아래 한 줄을 추가해야 필드의 `@Qualifier`가 생성자 파라미터까지 전파됩니다.
> ```
> lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Qualifier
> ```

### 5-5. 대화방(conversationId)별로 기억을 구분하기

```java
public String chat(ChatDTO dto) {
    return chatClient.prompt()
            .system("친절하게 50자 이내로 한글로 대답")
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, dto.conversationId()))
            .user(dto.message())
            .call().content();
}
```

- `MessageChatMemoryAdvisor`는 `advisors(a -> a.param(ChatMemory.CONVERSATION_ID, ...))`로 넘겨준 대화 ID를 기준으로 "이 대화방의 이전 메시지들"을 찾아서 자동으로 프롬프트에 끼워 넣어줍니다.
- 이 프로젝트에서는 로그인 기능이 없어서, `HttpSession`의 세션 ID를 `conversationId`로 그대로 사용했습니다. (`session.getId()`)

## 6. 컨트롤러 - PRG(Post-Redirect-Get) 패턴 복습

```java
@PostMapping
public String chat2(ChatDTO dto, RedirectAttributes redirectAttributes, HttpSession session) {
    String result = chatService.chat(dto.withID(session.getId()));
    redirectAttributes.addFlashAttribute("result", result);
    return "redirect:/";
}
```

- 폼 제출(POST) 후 바로 화면을 그리지 않고 `redirect:/`로 GET 요청을 한 번 더 보냅니다.
- 새로고침해도 폼이 중복 제출되지 않도록 하는 패턴(예전에 배운 PRG 패턴)이 여기서도 그대로 쓰였습니다.
- `RedirectAttributes.addFlashAttribute()`는 리다이렉트 되는 딱 한 번의 요청에서만 살아있는 데이터를 세션에 임시로 담아 전달합니다.

`ChatDTO`도 record라서 불변(immutable)인데, 세션 ID를 나중에 채워 넣기 위해 아래처럼 "새 객체를 만들어 반환하는" 메서드를 추가했습니다.

```java
public record ChatDTO(String message, String conversationId) {
    public ChatDTO withID(String id) {
        return new ChatDTO(message, id);
    }
}
```

## 오늘의 핵심 정리

1. `ChatModel`(저수준) → `ChatClient`(고수준, 실제로 자주 쓰는 API)
2. 프롬프트는 `.user(u -> u.text(템플릿).param(키, 값))` 형태로 안전하게 조립
3. 구조화된 응답은 `.entity(Class)` 한 줄이면 되지만, 내부적으로는 `BeanOutputConverter`가 "포맷 지시문 추가 → JSON 응답 → 파싱" 3단계를 해주는 것
4. Advisor는 AI 호출 앞뒤로 로직을 끼워 넣는 인터셉터. `chain.nextCall()`을 꼭 호출해야 다음 단계로 진행됨
5. ChatMemory = 정책(`MessageWindowChatMemory`) + 저장소(`ChatMemoryRepository` 구현체 3종)로 역할이 분리됨
6. 같은 타입 빈이 여러 개면 `@Qualifier`로 구분, 롬복 생성자에 전파하려면 `lombok.config` 설정 필요
7. 대화방 구분은 `ChatMemory.CONVERSATION_ID` 파라미터로, 이 프로젝트는 세션 ID를 재사용
