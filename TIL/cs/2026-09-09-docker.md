# Docker Compose 오답노트 — 틀렸던 지점들, 그리고 왜 틀렸는지

## 실습 중 발생한 오류 6가지

### 1. 포트 매핑을 엉뚱한 서비스 밑에 선언함

**무엇을 했냐면**

`ports: ["9988:${SERVER_PORT}"]` 블록을 `app`이 아니라 `db` 서비스 아래에 적어버렸어요.

```yaml
services:
  db:
    image: mysql:8.0
    ports:
      - 9988:${SERVER_PORT}   # 여기 있으면 안 됨
  app:
    build: .
    # ports 항목이 없어서 호스트에 노출되지 않음
```

**왜 문제였냐면**

MySQL 컨테이너 내부엔 8080에서 듣는 프로세스가 없거든요. 도커는 호스트의 9988을 컨테이너 8080으로 넘기려다 상대가 없으니 연결을 끊었고, `curl`은 "Empty reply from server"를 돌려줬어요. 정작 8080에서 떠 있던 `app`은 호스트에 전혀 노출이 안 된 상태였고요.

**여기서 얻을 수 있는 교훈**

compose.yaml은 서비스별로 완전히 격리된 명세라는 거예요. `ports`, `environment`, `volumes` 같은 키는 그 값이 필요한 서비스의 들여쓰기 안에 있어야 하고, YAML 들여쓰기 한 칸 차이가 곧 "이 속성이 어느 컨테이너 것인가"를 결정해요.

> 연결 개념: 041 · slide 6 — compose.yaml 골격과 최상위 키

### 2. JDBC URL에 오타 (mysql → myysql)

**무엇을 했냐면**

```
spring.datasource.url=jdbc:myysql://mysql-db:3306/mydb
```

**왜 문제였냐면**

MySQL 드라이버가 `myysql`이라는 스킴을 인식 못 해서 URL 자체를 거부(`claims to not accept jdbcUrl`)했고, `HikariDataSource` 빈 생성이 실패하면서 애플리케이션이 시작조차 못 했어요.

**여기서 얻을 수 있는 교훈**

환경변수로 접속 정보를 코드 밖으로 분리해도, 그 값 자체가 오타면 아무 소용이 없어요. `.env`·`environment`로 아무리 중앙화해도 결국 사람이 타이핑한 문자열이라는 건 그대로거든요.

> 연결 개념: 041 · slide 7 — 설정 주입 경로: 변수 치환과 env_file

### 3. SPRING_SERVER_PORT — 존재하지 않는 환경변수

**무엇을 했냐면**

```yaml
environment:
  SPRING_SERVER_PORT: 8080   # 아무 프로퍼티에도 안 붙는다
```

**왜 문제였냐면**

스프링 부트의 relaxed binding은 프로퍼티 키를 대문자+언더스코어로 바꾼 이름을 환경변수로 인식해요. `server.port`는 `SERVER_PORT`가 맞고, `SPRING_` 접두사는 프로퍼티 키가 실제로 `spring.`으로 시작할 때만 붙어요(예: `spring.datasource.url` → `SPRING_DATASOURCE_URL`). 기본 포트가 마침 8080이라 우연히 안 들켰던 것뿐이었죠.

**여기서 얻을 수 있는 교훈**

"환경변수 이름 = 프로퍼티 키를 그대로 대문자화한 것"이 원칙이지, "SPRING_을 일단 붙이고 본다"는 아니에요. 포트를 바꾸는 순간 바로 드러났을 잠복 버그였어요.

### 4. nginx upstream이 존재하지 않는 서비스명을 가리킴

**무엇을 했냐면**

```nginx
location / {
    proxy_pass http://app1:8080;   # compose 서비스명은 app
}
```

**왜 문제였냐면**

nginx는 시작 시점에 `proxy_pass`의 호스트를 resolve하려고 시도해요. `app1`이라는 서비스는 존재하지 않으니 `host not found in upstream "app1"` emerg 에러로 아예 기동에 실패했고, 컨테이너는 몇 분째 재시작을 반복했어요.

**여기서 얻을 수 있는 교훈**

컴포즈 네트워크 안에서 다른 컨테이너를 가리킬 땐 반드시 **services: 아래 선언한 서비스 이름**을 DNS처럼 써야 해요. 컨테이너 이름(`container_name`)이나 임의의 별칭이 아니라, 정확히 그 서비스 키와 일치해야 하고요.

> 연결 개념: 042 · slide 9 — upstream 라운드로빈 설정 / 041 · slide 4 — 서비스 이름 조회: IP 대신 서비스명 db로 접근

### 5. nginx 서비스가 아예 어떤 네트워크에도 소속되지 않음

**무엇을 했냐면**

```yaml
nginx:
  image: nginx:alpine
  ports: ["81:80"]
  # networks: 항목 자체가 없음 → default 네트워크로 고립
```

**왜 문제였냐면**

`db`, `app`은 `backend-net`에 연결되어 있었는데 `nginx`는 어디에도 안 속해 있어서 같은 네트워크가 아니었어요. 서비스 이름을 정확히 고쳐도 애초에 통신 경로 자체가 없는 상태였던 거예요.

**여기서 얻을 수 있는 교훈**

3-Layer 격리 구조에서 네트워크 소속은 자동으로 생기지 않아요. "이 서비스가 어떤 사설망에 속하는가"를 서비스마다 명시해야 하고, 생략하면 도커가 알아서 연결해주는 게 아니라 오히려 고립돼요.

> 연결 개념: 042 · slide 4~5 — 3-Layer 아키텍처, 계층별 격리 비교

### 6. depends_on을 "DB 준비 완료 보장"으로 오해함 (제일 핵심)

**무엇을 했냐면**

```yaml
app:
  depends_on: [db]   # 시작 순서만 보장, 준비 상태는 모름
```

**왜 문제였냐면**

MySQL은 새 볼륨으로 처음 기동할 때 데이터 디렉토리 초기화에 몇 초에서 몇십 초까지 걸려요. `depends_on`은 "db 컨테이너 프로세스가 시작됐다"까지만 보장하지, "3306이 쿼리를 받을 준비가 됐다"는 보장 안 해줘요. 그 사이 앱이 먼저 연결을 시도했고, `Connection refused`로 기동 실패 → 재시작을 다섯 번쯤 반복하고 나서야 우연히 DB가 준비된 타이밍이랑 맞아 정상 기동됐어요.

**어떻게 고쳤냐면**

```yaml
db:
  healthcheck:
    test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
    interval: 5s
    timeout: 5s
    retries: 10
app:
  depends_on:
    db:
      condition: service_healthy
```

**여기서 얻을 수 있는 교훈**

강의자료 두 편 다 이 함정을 정확히 짚고 있어요. `depends_on`은 순서 보장이지 준비 보장이 아니라는 거죠. 강의자료는 "로그로 준비 완료를 확인한 뒤 `restart`"라는 임시 대응을 보여주는데, 실전에서는 `healthcheck` + `condition: service_healthy`로 아예 레이스 컨디션 자체를 없애는 게 더 근본적인 해법이에요.

> 연결 개념: 041 · slide 8, 19 — depends_on의 한계 / 구동 순서 문제와 준비 확인 / 042 · slide 13 — DB 준비 확인 후 재구동

## 기술면접 포인트 — version 필드를 안 쓰는 이유

강의자료에는 "표준이 Compose Specification으로 통합되어 버전 고정이 불필요하다"고만 짧게 나와 있어서, 면접에서 풀어 설명할 수 있게 좀 더 정리해봤어요.

**Q. compose.yaml 최상단에 `version: "3.8"` 같은 필드를 왜 안 쓰나요?**

예전에는 왜 필요했는지부터 보면, Docker Compose V1(파이썬으로 작성된 `docker-compose` CLI) 시절엔 Compose 파일 포맷 자체가 1, 2, 2.x, 3, 3.x 등으로 나뉘어 있었어요. 버전마다 지원하는 키도 달랐고요 — 예를 들면 3.x대에만 `deploy`(Swarm 관련) 키가 있었고, 2.x대엔 없었거든요. 그래서 파일 최상단에 `version:`을 명시해야 파서가 "이 파일을 어떤 스키마로 해석할지" 판단할 수 있었어요.

그런데 2020년쯤 Docker와 커뮤니티가 흩어져 있던 버전들을 하나의 오픈 표준인 **Compose Specification**으로 통합했어요. Go로 재작성된 Compose V2(지금 쓰는, 하이픈 없는 `docker compose` 서브커맨드)는 이 단일 스펙만 따르고요. 더 이상 major/minor 버전이라는 개념 자체가 없고, "이 스펙이 지원하는 최신 키인가 아닌가"만 남았어요.

그래서 지금은 `version:` 필드가 사실상 **deprecated**예요. 최신 Compose CLI는 이 필드를 만나면 그냥 무시하거나 `the attribute version is obsolete, it will be ignored` 경고를 띄워요. 파일 이름도 과거 관례였던 `docker-compose.yml` 대신 `compose.yaml`이 공식 권장 이름으로 자리잡는 추세고요.

> **한 문장으로 답한다면**
> "Compose V1 시절엔 파일 포맷이 버전별로 나뉘어 있어서 버전 명시가 필수였지만, 2020년 Compose Specification으로 표준이 통합되면서 버전 개념 자체가 사라졌습니다. 최신 Compose CLI에서는 `version` 필드가 deprecated라 굳이 넣으면 오히려 obsolete 경고가 뜨기 때문에 의도적으로 생략합니다."

## 면접 전 30초 체크리스트

| 개념 | 한 줄 정의 | 흔한 오해 |
|---|---|---|
| `depends_on` | 컨테이너 **시작 순서**만 제어함 | DB가 "준비"됐다는 뜻은 아님 — `condition: service_healthy` 필요 |
| 서비스 간 통신 | `services:` 아래 이름이 곧 **DNS 호스트명**이 됨 | `container_name`이나 임의 별칭으로는 못 찾음 |
| `networks:` | 서비스마다 소속을 **명시**해야 함 | 선언 안 하면 자동 연결이 아니라 default망으로 고립됨 |
| `.env` vs `environment` | `.env`는 변수 치환용, `environment`는 컨테이너 내부 주입용 | 둘 다 오타까지 잡아주진 않음 |
| 프로젝트 네임스페이스 | 디렉터리명(또는 `-p`)이 리소스 이름 접두어가 됨 | `container_name` 지정하면 `--scale` 못 씀 |
| `down` vs `down -v` | `-v`를 붙여야만 명명 볼륨까지 삭제됨 | 기본 `down`은 데이터 그대로 보존됨 |
| `version:` 필드 | Compose Specification 통합 이후 deprecated됨 | 최신 파일엔 의도적으로 생략하는 게 맞음 |
