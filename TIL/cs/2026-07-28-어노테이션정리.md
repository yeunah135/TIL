# 260729 어노테이션 정리 - Spring AI 프로젝트에 나온 어노테이션 모음 (상세판)

오늘 프로젝트에 등장한 어노테이션을 하나씩, **① 무엇인지 → ② 왜/언제 쓰는지 → ③ 실제 코드 예시 → ④ 안 쓰면 어떻게 되는지** 순서로 자세히 정리했습니다. 처음 보는 분도 이해할 수 있도록 비유를 함께 넣었습니다.

> 어노테이션(annotation)이란 `@`으로 시작하는 표시로, 코드 위에 붙여서 "이 클래스/메서드/필드는 이런 역할을 한다"고 스프링(또는 다른 프레임워크)에게 알려주는 **꼬리표** 같은 것입니다. 어노테이션 자체는 로직을 실행하지 않고, 프레임워크가 그 꼬리표를 보고 대신 코드를 만들어주거나 특별하게 처리해줍니다.

---

## 1. 빈(Bean) 등록 관련

스프링에서 "빈(Bean)"이란 **스프링이 대신 생성하고 관리해주는 객체**를 말합니다. 우리가 직접 `new`로 만드는 대신, 스프링에게 "이 객체는 네가 만들어서 필요한 곳에 꽂아줘"라고 맡기는 방식입니다.

### `@Configuration`

**무엇인지**: "이 클래스는 빈을 만드는 설정 전용 클래스입니다"라고 스프링에게 알려주는 표시입니다.

**언제 쓰나요**: 라이브러리(여기서는 Spring AI)가 자동으로 만들어주지 않는 빈을, 내가 직접 원하는 방식으로 조립해서 등록하고 싶을 때 사용합니다. 오늘 프로젝트에서는 `ChatMemory`(대화 몇 개까지 기억할지)와 `ChatClient`(AI 호출 객체)를 **3가지 방식(InMemory/MyBatis/JPA)으로 각각 다르게 조립**해야 했기 때문에, 스프링이 알아서 만들어주는 기본 빈만으로는 부족해서 직접 설정 클래스를 만들었습니다.

```java
@Configuration
public class ChatMemoryConfig {

    @Bean
    public ChatMemory inMemoryChatMemory() {
        return messageWindow(new InMemoryChatMemoryRepository());
    }
}
```

**비유**: 레시피북(=설정 클래스) 표지에 "여기 있는 요리법들은 다 진짜 요리로 만들어서 냉장고(=스프링 컨테이너)에 넣어둘 것"이라고 써 붙인 것과 같습니다. `@Configuration`이 그 표지 역할입니다.

**안 붙이면**: 안에 있는 `@Bean` 메서드가 있어도 스프링이 이 클래스를 설정 클래스로 인식하지 못해서, 빈이 등록되지 않습니다. (엄밀히는 `@Component`류만 있어도 일부 동작하지만, 일반적으로 `@Bean`을 쓰려면 `@Configuration`과 짝을 이룹니다.)

---

### `@Bean`

**무엇인지**: 메서드 위에 붙여서, **이 메서드가 반환하는 객체를 스프링 컨테이너에 등록**하겠다는 표시입니다.

**언제 쓰나요**: 내가 직접 `new`로 만들어야 하는 복잡한 객체(설정값이 여러 개 필요하거나, 다른 빈을 조합해서 만들어야 하는 경우)를 빈으로 등록하고 싶을 때 사용합니다.

```java
@Bean
public ChatMemory inMemoryChatMemory() {
    return messageWindow(new InMemoryChatMemoryRepository());
}

@Bean
public ChatClient inMemoryChatClient(
        ChatModel chatModel, // 스프링이 이미 등록해둔 빈을 파라미터로 자동으로 받아옴
        @Qualifier("inMemoryChatMemory") ChatMemory memory) {
    return chatClientWith(chatModel, memory);
}
```

- 메서드 이름(`inMemoryChatMemory`)이 그대로 **빈의 이름**이 됩니다. 이 이름은 나중에 `@Qualifier("inMemoryChatMemory")`에서 그대로 다시 사용합니다.
- 메서드의 파라미터(`ChatModel chatModel`)는 스프링이 "어? 이 타입의 빈이 이미 있네?" 하고 자동으로 찾아서 넣어줍니다. 이걸 **의존성 주입(Dependency Injection)**이라고 부릅니다.

**비유**: 레시피북 안의 "김치찌개 만드는 법" 한 페이지가 `@Bean` 메서드 하나입니다. 그 페이지대로 만든 실제 요리(=객체)를 냉장고(=스프링 컨테이너)에 넣어두는 것입니다.

**안 쓰면**: 그 객체가 스프링 컨테이너에 등록되지 않으므로, 다른 클래스에서 `@Autowired`나 생성자 주입으로 가져다 쓸 수 없습니다. 매번 직접 `new ChatMemory(...)`를 해줘야 하고, 그럼 `@Qualifier`로 여러 개를 구분해서 쓰는 것도 불가능해집니다.

---

### `@Qualifier("빈이름")`

**무엇인지**: 같은 타입의 빈이 여러 개 있을 때, "이름"으로 정확히 어떤 빈을 쓸지 콕 집어주는 표시입니다.

**언제 쓰나요**: 오늘 프로젝트처럼 `ChatMemory` 타입 빈이 `inMemoryChatMemory`, `mybatisChatMemory`, `jpaChatMemory` 이렇게 3개나 등록되어 있으면, 스프링은 "`ChatMemory`를 넣어달라"는 요청을 받았을 때 **어떤 걸 넣어야 할지 알 수 없어서 에러**가 납니다. 이럴 때 이름으로 구분해줘야 합니다.

```java
// 빈을 "만들 때" - 어떤 ChatMemory를 재료로 쓸지 지정
@Bean
public ChatClient jpaChatClient(
        ChatModel chatModel,
        @Qualifier("jpaChatMemory") ChatMemory memory) {
    return chatClientWith(chatModel, memory);
}
```

```java
// 빈을 "가져다 쓸 때" - 어떤 ChatClient를 주입받을지 지정
@Service
@RequiredArgsConstructor
public class ChatService2 {
    @Qualifier("jpaChatClient")
    private final ChatClient chatClient;
}
```

**비유**: 냉장고에 "김치찌개"가 3통(맵게/보통/순하게) 있다고 상상해보세요. "김치찌개 좀 줘"라고만 하면 어떤 걸 줘야 할지 모릅니다. `@Qualifier("순한맛")`처럼 이름표를 딱 지정해줘야 정확히 원하는 통을 꺼내줄 수 있습니다.

**주의 - 오늘 겪은 실제 문제점**: 롬복의 `@RequiredArgsConstructor`는 필드 위에 붙은 `@Qualifier`를 자동으로 생성자 파라미터까지 옮겨주지 않습니다. (롬복은 기본적으로 다른 어노테이션을 "모르는 척" 무시하기 때문입니다.) 그래서 아래 설정을 `lombok.config` 파일에 추가해야 정상 동작합니다.

```
lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Qualifier
```

**안 쓰면**: `Field/parameter chatClient in ChatService2 required a single bean, but 3 were found` 같은 에러가 나며 애플리케이션이 아예 실행되지 않습니다.

## 2. 계층(Layer) 표시 - "이 클래스는 스프링이 자동으로 찾아서 등록해줘"

아래 3개는 모두 **스프링에게 "이 클래스도 빈으로 등록해줘"라고 자동으로 알려주는 표시**입니다. `@Bean`처럼 직접 만드는 대신, 클래스 위에 표시만 해두면 스프링이 프로젝트를 스캔하다가 알아서 등록해줍니다. 세 개 모두 내부적으로는 `@Component`라는 어노테이션을 포함하고 있어서 동작 원리는 동일하고, **이름만 다르게 붙여서 "이 클래스가 어떤 역할을 하는지" 사람이 읽기 쉽게 구분**하는 용도입니다.

### `@Controller`

**무엇인지**: 사용자의 웹 요청(URL 접속)을 가장 먼저 받는 역할을 하는 클래스라는 표시입니다.

**언제 쓰나요**: 사용자가 브라우저로 `/`에 접속하거나, 폼을 제출(POST)했을 때 그 요청을 받아서 처리할 클래스에 붙입니다.

```java
@Controller
@RequestMapping
public class MainController {
    // 사용자의 요청을 받아서, Service를 호출하고, 결과를 화면(View)에 전달
}
```

**비유**: 식당의 "홀 서빙 직원"입니다. 손님(사용자)의 주문(요청)을 가장 먼저 받고, 주방(Service)에 전달한 뒤, 완성된 요리(결과)를 다시 손님 테이블(화면)로 가져다줍니다.

**안 쓰면**: 스프링이 이 클래스를 웹 요청을 처리하는 빈으로 인식하지 못해서, `/`로 접속해도 이 클래스의 메서드가 실행되지 않고 404 에러가 납니다.

---

### `@Service`

**무엇인지**: 실제 비즈니스 로직(핵심 처리 과정)을 담당하는 클래스라는 표시입니다.

**언제 쓰나요**: "AI에게 질문을 보내고 답변을 받아온다", "결제를 처리한다"처럼 애플리케이션의 **핵심 기능**을 담당하는 클래스에 붙입니다. 오늘 프로젝트에서는 `ChatService`, `ChatService2`가 실제로 `ChatClient`를 사용해서 AI를 호출하는 로직을 담당했습니다.

```java
@Service
public class ChatService {
    private final ChatModel chatModel;
    private final ChatClient chatClient;

    public ChatService(ChatModel chatModel) {
        this.chatModel = chatModel;
        this.chatClient = ChatClient.builder(chatModel).build();
    }

    public String chat(ChatDTO dto) {
        // AI 호출하는 핵심 로직
    }
}
```

**비유**: 식당의 "주방(요리사)"입니다. 홀 직원(Controller)에게 주문을 받아서, 실제로 재료(데이터)를 손질하고 요리(로직 처리)를 하는 곳입니다.

**안 쓰면**: 이 클래스가 빈으로 등록되지 않아서, `Controller`에서 `private final ChatService chatService;` 처럼 주입받으려 해도 "그런 빈이 없다"는 에러가 발생합니다.

---

### `@Repository`

**무엇인지**: 데이터를 저장하거나 조회하는 역할을 하는 클래스라는 표시입니다.

**언제 쓰나요**: DB에 데이터를 넣거나 꺼내오는 클래스에 붙입니다. 오늘 프로젝트에서는 대화 내역을 DB에 저장/조회하는 `JpaChatMemoryRepository`, `MyBatisChatMemoryRepository`에 사용했습니다.

```java
@Repository
@RequiredArgsConstructor
public class JpaChatMemoryRepository implements ChatMemoryRepository {
    private final ChatMemoryJpaRepository repository;

    @Override
    public List<Message> findByConversationId(String conversationId) {
        return repository.findAllByConversationId(conversationId)
                .stream()
                .map(ChatMessageJPA::toMessage)
                .toList();
    }
}
```

**비유**: 식당의 "창고 관리 담당자"입니다. 재료(데이터)가 어디에 몇 개 있는지 확인하고, 꺼내오고, 새로 채워 넣는 역할을 합니다.

**`@Service`, `@Controller`와 다른 점**: `@Repository`는 추가로 "DB 작업 중 발생하는 여러 종류의 예외(SQLException 등)를 스프링이 이해하는 공통 예외로 자동 변환"해주는 기능이 하나 더 있습니다. (단순히 이름만 다른 게 아니라 이 부분만 살짝 더 특별합니다.)

**안 쓰면**: 클래스 자체는 컴파일되지만, 빈으로 등록되지 않아서 다른 곳에서 주입받아 쓸 수 없습니다.

---

## 3. 요청 매핑 (Controller에서 URL과 메서드를 연결하기)

### `@RequestMapping`

**무엇인지**: 이 컨트롤러(또는 메서드)가 어떤 URL 경로를 처리할지 지정하는 어노테이션입니다.

**언제 쓰나요**: 클래스 전체에 공통 경로를 지정하고 싶을 때 클래스 위에 붙입니다. 오늘 프로젝트는 값을 비워서(`@RequestMapping`만) 사용했는데, 이 경우 기본 경로 `/`를 의미합니다.

```java
@Controller
@RequestMapping
public class MainController {
```

**비유**: 우체국에서 "이 창구는 1~10번 우편번호 담당입니다"라고 팻말을 붙여두는 것과 비슷합니다.

---

### `@GetMapping` / `@PostMapping`

**무엇인지**: HTTP 요청 방식(GET 또는 POST)에 따라 어떤 메서드가 그 요청을 처리할지 연결해주는 어노테이션입니다.

**언제 쓰나요**:
- `@GetMapping` : 브라우저에서 페이지를 "조회"할 때 (주소창에 입력하거나 링크 클릭). 오늘 프로젝트에서는 대화 목록을 보여주는 화면을 그릴 때 사용했습니다.
- `@PostMapping` : 폼을 "제출"할 때처럼 서버에 데이터를 보내서 무언가를 처리해야 할 때 사용했습니다. (여기서는 사용자의 질문을 AI에게 보낼 때)

```java
@GetMapping
public String index(Model model, HttpSession session) {
    model.addAttribute("history", chatService.getHistory(session.getId()));
    return "index"; // index.jsp를 보여줌
}

@PostMapping
public String chat2(ChatDTO dto, RedirectAttributes redirectAttributes, HttpSession session) {
    String result = chatService.chat(dto.withID(session.getId()));
    redirectAttributes.addFlashAttribute("result", result);
    return "redirect:/"; // 처리 후 다시 GET으로 이동 (PRG 패턴)
}
```

**비유**: 같은 우체국 창구라도 "조회는 이 창구, 접수(제출)는 저 창구"로 나눠놓은 것과 같습니다. GET은 "구경만 하기", POST는 "무언가를 맡기기(제출하기)"라고 기억하면 쉽습니다.

**안 쓰면**: 브라우저가 `/`로 GET 요청을 보내거나 폼이 POST 요청을 보내도, 어떤 메서드가 그 요청을 처리해야 할지 스프링이 몰라서 404 에러가 납니다.

## 4. 롬복(Lombok) - 반복되는 코드를 자동으로 만들어주는 어노테이션

롬복은 Spring AI 라이브러리는 아니지만, "매번 손으로 치기 귀찮은 코드(getter, 생성자 등)"를 자동으로 만들어주는 도구라서 오늘 코드 전반에 계속 등장했습니다. 컴파일할 때 어노테이션이 붙은 자리에 실제 코드가 "끼워 넣어진다"고 생각하면 됩니다.

### `@Getter`

**무엇인지**: 클래스의 모든 필드에 대해 `get필드명()` 형태의 조회 메서드를 자동으로 만들어줍니다.

**언제 쓰나요**: DTO나 Entity처럼, 필드 값을 외부에서 읽기만 하면 되는 클래스에 붙입니다.

```java
@Getter
public class ChatMessageJPA {
    private String conversationId;
    private String content;
}
// 아래 코드가 자동으로 생겨서, chatMessage.getContent() 처럼 쓸 수 있게 됨
// public String getConversationId() { return conversationId; }
// public String getContent() { return content; }
```

**안 쓰면**: `getConversationId()`, `getContent()` 같은 메서드를 직접 손으로 하나하나 작성해야 합니다.

---

### `@Builder`

**무엇인지**: 객체를 만들 때 `new`로 순서대로 값을 넣는 대신, **필드 이름을 명시하면서 하나씩 값을 채워 넣을 수 있는 빌더 패턴** 코드를 자동으로 만들어줍니다.

**언제 쓰나요**: 필드가 여러 개라서 `new ChatMessageJPA(1L, "conv1", "USER", "안녕", 0)`처럼 순서대로 값을 넘기면 어떤 값이 어떤 필드인지 헷갈릴 때 사용합니다.

```java
@Builder
public class ChatMessageJPA {
    private String conversationId;
    private String messageType;
    private String content;
    private int seq;
}

// 사용하는 곳
ChatMessageJPA.builder()
        .conversationId(conversationId)
        .messageType(message.getMessageType().name())
        .content(message.getText())
        .seq(seq)
        .build();
```

**비유**: 햄버거 가게에서 "패티 O, 치즈 X, 양상추 O" 처럼 원하는 재료 이름을 하나씩 말하면서 주문하는 것과 비슷합니다. `new`로 순서대로 넣는 방식은 "그냥 순서대로 다 말해주세요"에 가까워서 실수하기 쉽습니다.

**안 쓰면**: `.builder()`를 쓸 수 없고, 생성자로 순서에 맞춰 값을 넣어야 해서 필드 순서를 착각하면 버그가 생기기 쉽습니다.

---

### `@NoArgsConstructor` / `@AllArgsConstructor`

**무엇인지**:
- `@NoArgsConstructor` : 파라미터가 하나도 없는 기본 생성자를 자동으로 만들어줍니다. (`new ChatMessageJPA()`)
- `@AllArgsConstructor` : 모든 필드를 파라미터로 받는 생성자를 자동으로 만들어줍니다. (`new ChatMessageJPA(id, conversationId, messageType, content, seq)`)

**언제 쓰나요**: JPA 엔티티는 두 생성자가 **함께 필요**합니다.
- `@NoArgsConstructor`가 필요한 이유: JPA(Hibernate)가 DB에서 데이터를 읽어와 객체를 만들 때, 내부적으로 빈 객체를 먼저 만든 뒤 리플렉션으로 값을 채워 넣는 방식을 쓰기 때문에 파라미터 없는 생성자가 반드시 있어야 합니다.
- `@AllArgsConstructor`가 필요한 이유: `@Builder`가 내부적으로 모든 필드를 받는 생성자를 사용해서 객체를 조립하기 때문입니다.

```java
@Getter
@Builder
@NoArgsConstructor
@AllArgsConstructor
@Entity
public class ChatMessageJPA {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String conversationId;
    private String messageType;
    private String content;
    private int seq;
}
```

**안 쓰면**: `@NoArgsConstructor`가 없으면 JPA 엔티티 로딩 시 `NoSuchMethodException` 계열 오류가 나거나, Hibernate가 이 클래스를 엔티티로 다루지 못합니다. `@AllArgsConstructor`가 없으면 `@Builder`가 사용할 생성자가 없어서 컴파일 에러가 납니다.

---

### `@RequiredArgsConstructor`

**무엇인지**: `final`이 붙은 필드만 파라미터로 받는 생성자를 자동으로 만들어줍니다.

**언제 쓰나요**: **의존성 주입(다른 빈을 필드로 가져오는 것)**을 할 때 가장 많이 쓰는 방식입니다. 스프링은 생성자가 하나뿐이면 그 생성자를 자동으로 사용해서 필요한 빈들을 주입해주기 때문에, 이 어노테이션 하나로 "생성자를 통한 의존성 주입"을 간단하게 끝낼 수 있습니다.

```java
@Service
@RequiredArgsConstructor
public class ChatService2 {
    @Qualifier("jpaChatClient")
    private final ChatClient chatClient;
    private final MyBatisChatMemoryRepository chatMemoryRepository;
    // 아래 생성자가 자동으로 생겨서, 스프링이 이 생성자로 빈을 주입해줌
    // public ChatService2(ChatClient chatClient, MyBatisChatMemoryRepository chatMemoryRepository) { ... }
}
```

**비유**: "이 부품(final 필드)들이 없으면 이 기계(클래스)는 아예 조립이 안 됩니다"라고 미리 못박아두는 것과 같습니다. `final`이라서 한 번 주입받으면 중간에 다른 걸로 바꿔치기할 수도 없습니다. (안정성을 위해 `@Autowired` 필드 주입보다 이 방식이 권장됩니다.)

**안 쓰면**: 생성자를 직접 작성하거나, `@Autowired`를 필드에 붙여서 주입받아야 합니다.

---

### `@Slf4j`

**무엇인지**: `log`라는 이름의 로거(Logger) 객체를 클래스에 자동으로 만들어줍니다.

**언제 쓰나요**: 콘솔에 로그(실행 기록)를 남기고 싶을 때, 매번 `Logger log = LoggerFactory.getLogger(클래스명.class);` 라고 직접 쓰는 대신 이 어노테이션 한 줄로 끝냅니다.

```java
@Slf4j
public class TimingLoggerAdvisor implements CallAdvisor {

    @Override
    public ChatClientResponse adviseCall(ChatClientRequest request, CallAdvisorChain chain) {
        log.info("[TimingLoggerAdvisor] 시작 : prompt: {}", request.prompt().getContents());
        ...
    }
}
```

- `{}` 부분은 문자열을 합칠 필요 없이 뒤에 오는 값(`request.prompt().getContents()`)이 자동으로 채워집니다.

**안 쓰면**: `private static final Logger log = LoggerFactory.getLogger(TimingLoggerAdvisor.class);` 를 직접 한 줄 써야 합니다. (짧은 코드지만 클래스마다 반복되면 귀찮습니다.)

## 5. JPA 관련

### `@Entity`, `@Table(name = "...")`

**무엇인지**:
- `@Entity` : 이 클래스가 **DB의 테이블 한 줄(row)과 매핑되는 객체**라는 표시입니다.
- `@Table(name = "chat_message")` : 어떤 테이블 이름과 매핑할지 명시적으로 지정합니다. (생략하면 클래스 이름을 그대로 테이블 이름으로 사용)

**언제 쓰나요**: DB 테이블 하나를 자바 객체로 다루고 싶을 때, 그 객체 클래스에 붙입니다.

```java
@Table(name = "chat_message")
@Entity
public class ChatMessageJPA {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String conversationId;
}
```

**비유**: 엑셀 시트(테이블)의 한 행을 자바 객체 하나로 옮겨 담는다고 생각하면 됩니다. `@Entity`는 "이 객체는 엑셀 행과 짝지어져 있다"는 표시입니다.

**안 쓰면**: JPA(Hibernate)가 이 클래스를 테이블과 연결된 대상으로 인식하지 못해서, `JpaRepository`로 저장/조회를 시도할 때 매핑 오류가 발생합니다.

---

### `@Id`, `@GeneratedValue`

**무엇인지**:
- `@Id` : 이 필드가 테이블의 **기본키(Primary Key)**, 즉 각 행을 구분하는 고유값이라는 표시입니다.
- `@GeneratedValue(strategy = GenerationType.IDENTITY)` : 이 기본키 값을 개발자가 직접 정하지 않고, **DB의 AUTO_INCREMENT 기능에 맡겨서 자동으로 1씩 증가**시키겠다는 뜻입니다.

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

**언제 쓰나요**: 새로운 데이터를 저장할 때마다 고유 번호가 자동으로 매겨져야 하는 필드에 사용합니다. (오늘 프로젝트의 `id` 필드처럼)

**안 쓰면**: `@Id`가 없으면 "이 엔티티에는 기본키가 없다"는 에러가 나서 애플리케이션이 시작조차 되지 않습니다. `@GeneratedValue`가 없으면 저장할 때마다 `id` 값을 직접 지정해서 넣어줘야 합니다.

---

### `@Transactional`

**무엇인지**: 메서드 안의 여러 DB 작업을 **하나의 트랜잭션(작업 묶음)**으로 처리하도록 만들어줍니다. 트랜잭션이란 "여러 작업을 전부 성공하거나, 전부 실패로 되돌리거나(롤백) 둘 중 하나만 있게 만드는 단위"입니다.

**언제 쓰나요**: 서로 연결된 여러 DB 작업이 있어서, 중간에 하나라도 실패하면 전체를 취소해야 할 때 사용합니다.

```java
@Override
@Transactional
public void saveAll(String conversationId, List<Message> messages) {
    repository.deleteAllByConversationId(conversationId); // 1. 기존 대화 삭제
    // ...
    repository.saveAll(chatMessages); // 2. 새 대화 저장
}
```

만약 "1. 삭제"는 성공했는데 "2. 저장"에서 에러가 나면, `@Transactional` 덕분에 삭제했던 것도 자동으로 취소(롤백)되어서 **"대화 내용이 통째로 날아가는" 최악의 상황을 막아줍니다.**

**비유**: 계좌 이체를 생각하면 쉽습니다. "내 계좌에서 돈 빼기"는 성공했는데 "상대 계좌에 돈 넣기"에서 에러가 나면, 돈이 그냥 사라져버리면 안 되겠죠. `@Transactional`은 이 두 작업을 묶어서 "둘 다 성공 or 둘 다 취소"로 만들어줍니다.

**안 쓰면**: 두 작업 중 하나만 성공하고 하나는 실패하는 **데이터 불일치 상태**가 발생할 수 있습니다.

---

### `@Query`

**무엇인지**: Spring Data JPA가 메서드 이름만으로 자동 생성하기 어려운 쿼리를, **JPQL(자바 객체 기준 쿼리 언어)을 직접 작성**해서 지정하는 어노테이션입니다.

**언제 쓰나요**: `DISTINCT`, 복잡한 조인처럼 메서드 이름 규칙(`findByXxx`)만으로 표현하기 애매한 쿼리가 필요할 때 사용합니다.

```java
public interface ChatMemoryJpaRepository extends JpaRepository<ChatMessageJPA, Long> {

    List<ChatMessageJPA> findAllByConversationId(String conversationId); // 이름 규칙만으로 자동 생성됨 (Query Method)

    @Query("SELECT DISTINCT cm.conversationId FROM ChatMessageJPA cm") // 직접 작성한 쿼리
    List<String> findConversationIds();

    void deleteAllByConversationId(String conversationId); // 이것도 이름 규칙만으로 자동 생성됨
}
```

**알아두면 좋은 점**: 위 3개 메서드 중 `@Query`가 붙은 건 하나뿐입니다. 나머지 둘은 `findAllBy필드명`, `deleteAllBy필드명`처럼 **정해진 이름 패턴만 지키면 Spring Data JPA가 알아서 쿼리를 만들어주기 때문**에 어노테이션이 필요 없습니다. `@Query`는 그 패턴으로 해결이 안 될 때만 쓰는 "예외 상황용" 어노테이션입니다.

## 6. MyBatis 관련

### `@Mapper`

**무엇인지**: 이 인터페이스가 **MyBatis의 매퍼(Mapper)**임을 선언하는 표시입니다. 매퍼란 자바 메서드 호출을 실제 SQL 실행으로 연결해주는 다리 역할을 합니다.

**언제 쓰나요**: JPA처럼 자동으로 쿼리를 만들어주는 게 아니라, SQL을 **직접 XML에 작성해서 세밀하게 제어**하고 싶을 때 MyBatis를 사용하며, 그 인터페이스에 이 어노테이션을 붙입니다.

```java
@Mapper
public interface ChatMessageMapper {
    List<String> findConversationIds();
    List<ChatMessageMyBatis> findByConversationId(String conversationId);
    void insertAll(List<ChatMessageMyBatis> messages);
    void deleteByConversationId(String conversationId);
}
```

이 인터페이스의 메서드 이름(`findConversationIds`)은 같은 이름의 SQL(`id="findConversationIds"`)이 적힌 XML 파일과 자동으로 연결됩니다.

```xml
<!-- ChatMessageMapper.xml -->
<mapper namespace="org.example.springai2.mapper.ChatMessageMapper">
    <select id="findConversationIds" resultType="string">
        SELECT DISTINCT conversation_id
        FROM chat_message
    </select>
</mapper>
```

**비유**: `@Mapper`가 붙은 인터페이스는 "주문서 양식"이고, XML 파일은 "그 주문서를 받으면 실제로 어떻게 요리할지 적힌 레시피"입니다. 메서드 이름과 `id` 값이 똑같아야 서로 짝을 찾을 수 있습니다.

**JPA와 차이점 (오늘 두 방식을 비교하며 확인한 부분)**: JPA는 메서드 이름 규칙이나 `@Query`(JPQL)로 쿼리를 다루는 반면, MyBatis는 **진짜 SQL 문법 그대로**를 XML에 씁니다. 복잡한 SQL을 세밀하게 직접 제어하고 싶다면 MyBatis, 객체 중심으로 간편하게 다루고 싶다면 JPA가 더 편합니다.

**안 쓰면**: 스프링이 이 인터페이스를 MyBatis 매퍼로 인식하지 못해서, "구현체가 없다(No qualifying bean)"는 에러가 발생하며 이 인터페이스를 주입받는 다른 클래스가 실행되지 않습니다.

## 7. (참고) Spring AI 관련 인터페이스/클래스 — 어노테이션은 아니지만 함께 알아두면 좋은 것들

Spring AI는 신기하게도 오늘 다룬 기능 대부분이 **어노테이션이 아니라 인터페이스 구현 + 빌더 패턴**으로 이루어져 있습니다. 그래서 헷갈리지 않도록 짝지어 정리해둡니다.

| 이름 | 종류 | 언제/왜 쓰는지 |
|---|---|---|
| `CallAdvisor` | 인터페이스 | AI 호출 앞뒤로 로직(로깅, 시간 측정 등)을 끼워넣는 커스텀 Advisor를 만들고 싶을 때 직접 구현 (`TimingLoggerAdvisor`) |
| `ChatMemoryRepository` | 인터페이스 | 대화 기록을 "어디에" 저장할지 직접 정의하고 싶을 때 구현 (InMemory/MyBatis/JPA 3가지 버전) |
| `MessageWindowChatMemory` | 빌더 클래스 | 대화 기록을 "몇 개까지" 기억할지 같은 정책을 설정할 때 사용 (`.maxMessages(3)`) |
| `MessageChatMemoryAdvisor` | 빌더 클래스 | 위에서 만든 `ChatMemory`를 실제 `ChatClient`에 연결해서, 이전 대화가 자동으로 프롬프트에 포함되게 해줌 |

## 전체 요약 표

| 어노테이션 | 분류 | 붙이는 위치 | 한 줄 설명 |
|---|---|---|---|
| `@Configuration` | 빈 설정 | 클래스 | 빈을 만드는 설정 클래스임을 표시 |
| `@Bean` | 빈 설정 | 메서드 | 메서드 반환값을 스프링 빈으로 등록 |
| `@Qualifier("이름")` | 빈 설정 | 파라미터/필드 | 같은 타입 빈이 여러 개일 때 이름으로 구분해서 주입 |
| `@Controller` | 계층 | 클래스 | 웹 요청을 받아 화면(View)을 반환하는 계층 |
| `@Service` | 계층 | 클래스 | 핵심 비즈니스 로직을 담당하는 계층 |
| `@Repository` | 계층 | 클래스 | DB 저장/조회를 담당하는 계층 (예외 변환 기능 추가) |
| `@RequestMapping` | 매핑 | 클래스/메서드 | 기본 URL 경로 지정 |
| `@GetMapping` | 매핑 | 메서드 | GET(조회) 요청 처리 메서드 지정 |
| `@PostMapping` | 매핑 | 메서드 | POST(제출/처리) 요청 처리 메서드 지정 |
| `@Getter` | 롬복 | 클래스 | 모든 필드의 getter 메서드 자동 생성 |
| `@Builder` | 롬복 | 클래스 | 빌더 패턴 코드 자동 생성 |
| `@NoArgsConstructor` | 롬복 | 클래스 | 파라미터 없는 기본 생성자 자동 생성 (JPA 필수) |
| `@AllArgsConstructor` | 롬복 | 클래스 | 모든 필드를 받는 생성자 자동 생성 (`@Builder`가 사용) |
| `@RequiredArgsConstructor` | 롬복 | 클래스 | `final` 필드만 받는 생성자 자동 생성 (의존성 주입용) |
| `@Slf4j` | 롬복 | 클래스 | `log` 로거 객체 자동 생성 |
| `@Entity` | JPA | 클래스 | DB 테이블과 매핑되는 클래스임을 선언 |
| `@Table(name=...)` | JPA | 클래스 | 매핑할 테이블 이름 지정 |
| `@Id` | JPA | 필드 | 기본키(PK) 필드 지정 |
| `@GeneratedValue` | JPA | 필드 | 기본키 값을 DB가 자동 생성하도록 지정 |
| `@Transactional` | JPA | 메서드 | 여러 DB 작업을 하나의 트랜잭션(성공/롤백 묶음)으로 처리 |
| `@Query` | JPA | 메서드 | 이름 규칙으로 안 되는 쿼리를 JPQL로 직접 작성 |
| `@Mapper` | MyBatis | 인터페이스 | XML에 작성된 SQL과 연결되는 매퍼임을 선언 |
