# 🚀 AI 서비스 비용 최적화 및 네트워크 레이턴시 개선 프로젝트

본 프로젝트는 취업 준비 및 포트폴리오 시연 목적의 인프라 구축 과정에서 발생할 수 있는 **비용 부담을 제로(0원)**로 낮추면서도, 국내 사용자(면접관)에게 **상용 서비스 수준의 빠른 속도(Low Latency)**를 제공하기 위해 아키텍처를 설계하고 최적화한 경험을 다룹니다.

---

## 🛠️ 인프라 아키텍처 (Infrastructure Architecture)

비용 0원을 유지하되, 모든 인프라를 **한국(서울) 리전**으로 통일하여 네트워크 트래픽 효율을 극대화했습니다.

| 계층 (Layer) | 선택한 기술 / 플랫폼 | 적용 리전 (Region) | 비용 (Cost) | 선택 이유 및 핵심 전략 |
| :--- | :--- | :--- | :--- | :--- |
| **Frontend** | React / Next.js | **Vercel** (`icn1` - 서울) | 평생 무료 | 무중단(No Cold Start) 및 빠른 정적 페이지 서빙 |
| **Backend** | Java / Spring Boot | **Kakao Cloud** (`m1a.tiny`) | 평생 무료 | 익숙한 Spring Boot 프레임워크 구동 가능한 무료 VM |
| **Database** | Supabase (PostgreSQL) | **AWS** (`ap-northeast-2` - 서울) | 무료 티어 | 관계형 데이터 인프라 확보 및 백엔드와의 근접성 |
| **AI Engine** | Gemini 1.5 Flash / Pro | **Google AI Studio** | 무료 티어 | 인하우스 GPU 서버 비용 우회, 구글 인프라 연동 |

## 💡 주요 기술적 의사결정 및 문제 해결 (Technical Decision & Trouble Shooting)

### 1. 인하우스 GPU 구축 비용 우회를 통한 '비용 제로(0원)' 달성
* **문제 상황**: LLM(대형 언어 모델) 등 무거운 AI 연산을 서버 내에서 직접 처리하려면 고사양 GPU/CPU 서버가 필요하며, 취준생 수준에서 수십만 원 상당의 인프라 유지 비용이 발생하는 부담이 있었습니다.
* **해결 방안**: 대형 AI 모델을 자체 서버에 서빙하는 대신, 구글의 **Gemini API(Google AI Studio 무료 티어)**를 활용한 온디맨드(On-demand) AI 연산 중계 방식으로 아키텍처를 전환했습니다. 
* **성과**: 인프라 유지 비용을 **완전한 0원으로 방어**하는 동시에 구글의 상용 최신 AI 인프라를 안정적으로 포트폴리오에 도입했습니다.

### 2. Network Latency 최소화를 위한 '국내 리전(Seoul Region)' 단일화
* **문제 상황**: 대부분의 해외 무료 클라우드(미국/유럽 리전)는 국내 사용자(면접관) 기준 데이터 전송 물리적 거리가 멀어 사이트 진입 및 AI API 호출 시 체감 레이턴시(속도 지연)가 높다는 한계가 있었습니다.
* **해결 방안**: 웹 인프라 전 구간의 통신 최적화를 위해 **국내 인프라 단일화** 설정을 진행했습니다.
  * **Vercel Frontend**: 기본 설정(미국 동부) 대신 명시적으로 **Seoul, South Korea (`icn1`)** 리전 배포 설정.
  * **Spring Boot Backend**: 국내 초고속 백본망 인프라를 지닌 **카카오클라우드(Kakao Cloud) 서울 리전**에 가상 서버(VM) 배치.
  * **Database**: AWS 서울 리전 기반의 **Supabase** 데이터베이스 연동.
* **성과**: 글로벌 트래픽 낭비를 제거하고 전 구간을 국내 통신망으로 고정하여 **체감 응답 속도 및 페이지 로딩 성능을 획기적으로 개선**했습니다.

### 3. 한정된 가용 자원(1GB RAM) 환경에서의 Spring Boot 최적화
* **문제 상황**: 카카오클라우드 프리티어 VM은 **1GB RAM**의 타이트한 스펙을 가집니다. 구동 시 무거운 메모리를 상시 점유하는 Java Spring Boot 특성상 애플리케이션 빌드 및 실행 중 Out of Memory(OOM) 에러로 서버가 다운되는 리스크가 존재했습니다.
* **해결 방안**: 제한된 하드웨어 자원의 한계를 소프트웨어 튜닝으로 극복했습니다.
  * **Swap Memory 도입**: 리눅스 OS 레벨에서 하드디스크의 일부 공간을 메모리처럼 활용하는 **2GB 크기의 스왑 파일(Swap File)**을 생성하여 물리적 RAM 한계를 보완했습니다.
  * **JVM 메모리 옵션 조정**: Java 가상 머신 구동 스크립트에 `-Xms512m -Xmx512m` 등의 힙 메모리 상/하한선(Heap Size)을 강제 지정하여 인스턴스가 급격한 가비지 컬렉션(GC) 부하로 뻗는 현상을 사전에 제어했습니다.
* **성과**: 추가 비용 지출 없이 서버 자원을 소프트웨어적으로 확장하여 **Spring Boot 웹 서버를 24시간 무중단으로 안정성 있게 구동**하는 데 성공했습니다.

### 4. Connection Timeout 방지 및 UX 향상을 위한 Streaming API 도입
* **문제 상황**: AI 모델의 추론 과정이 길어지면 Vercel이나 외부 게이트웨이의 웹 서버 제한 시간(10~15초 제한)을 초과하여 **Connection Timeout 에러**가 유발되고, 유저는 답변이 올 때까지 빈 화면을 보며 이탈할 가능성이 높았습니다.
* **해결 방안**: Gemini API의 응답 방식을 단발성 REST 통신 대신 **Server-Sent Events(SSE) 기반의 스트리밍(Streaming) 방식**으로 변환했습니다. 백엔드가 구글로부터 받은 AI 답변 데이터를 실시간으로 프론트엔드에 한 글자씩 밀어 넣어주는(Push) 파이프라인을 구축했습니다.
* **성과**: 서버의 타임아웃 제한 조건 문제를 완벽하게 우회함과 동시에, 유저가 실시간 타자 연출(Typing Effect) 효과를 체감하게 하여 **서비스 신뢰도 및 사용자 경험(UX) 가치를 극대화**했습니다.
