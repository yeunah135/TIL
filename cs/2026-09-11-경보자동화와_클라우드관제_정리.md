# 경보 자동화와 클라우드 관제 — 수업 정리

> 원본 자료: 052_경보 자동화와 클라우드 관제_Alertmanager_GrafanaCloud.pdf

## 1. 전체 요약

### 핵심 개념

경보 파이프라인은 다음과 같이 이어집니다.

```
Spring Boot Actuator → Prometheus(규칙 평가) → Alertmanager(그룹핑/라우팅) → Slack / 이메일(아웃바운드 전송)
                              └──────────────→ Grafana Cloud(Remote Write, 원격 관제)
```

핵심은 **인바운드 포트를 하나도 열지 않고 전부 아웃바운드로만 동작**한다는 점입니다. 사내망 방화벽에 구멍을 내지 않고도, 내부 Prometheus가 HTTPS(443)로 Grafana Cloud에 지표를 밀어내는(push) 구조입니다.

경보는 4단계 상태 전이 모델을 따릅니다.

| 상태 | 의미 |
|---|---|
| `Inactive` | 조건식이 거짓으로 평가되는 정상 상태 |
| `Pending` | 조건은 참이나 `for` 시간을 채우지 못한 대기 상태 |
| `Firing` | `for` 시간 초과로 확정되어 Alertmanager로 라우팅 |
| `Resolved` | 정상 범위 복귀로 해제 메시지 자동 발송 |

`Pending` 구간은 일시적 스파이크를 걸러내는 **오탐 차단 버퍼**입니다.

### Alertmanager의 3대 핵심 메커니즘

| 메커니즘 | 기능 | 실무 적용 효과 |
|---|---|---|
| 그룹핑(Grouping) | 유사 경보 병합 | 동일 서비스·심각도의 다발성 경보를 1건으로 묶어 경보 피로 방지 |
| 중복 제거(Deduplication) | 동일 알림 필터링 | fingerprint 기준으로 중복 수신 패킷을 단일 통지로 제한 |
| 억제(Inhibition) | 하위 알림 음소거 | 상위 인프라 장애 시 종속 컨테이너의 연쇄 경보를 차단해 근본 원인에 집중 |

> 경보 피로(Alert Fatigue)는 알림이 부족해서가 아니라 **과잉**해서 생깁니다. 운영자가 알림을 음소거하는 순간 가장 치명적인 경보를 놓치게 됩니다.

### 모니터링 vs 관제

| 구분 | 모니터링(Monitoring) | 관제(Operations Control) |
|---|---|---|
| 핵심 목적 | 지표·로그의 계측과 수동적 상태 관측 | 가용성 보장 및 장애 시 능동적 통제·복구 |
| 핵심 도구 | Spring Boot Actuator, Prometheus, Loki | Alertmanager, On-Call 통지, 원격 대시보드 |

클라우드 통합 관제는 사내망 폐쇄성을 유지(아웃바운드 전송)하면서, 중앙 집중형 SaaS(Grafana Cloud)를 통해 언제 어디서나 전사 인프라를 **단일 접점(Single Pane of Glass)**에서 감시·통제하는 운영 체계입니다.

### 실습 로드맵 (8단계)

1. Grafana Cloud 준비와 Remote Write 토큰 발급 (`.env` 등록)
2. Prometheus Alerting Rule 작성 (`up == 0`, JVM 힙 임계식)
3. Alertmanager 설정과 리시버 정의 (Slack Webhook·SMTP 라우팅)
4. Prometheus 설정과 전체 스택 기동 (Alertmanager 연결 + Remote Write 동시 가동)
5. 장애 주입과 상태 전이 관측 (`Pending` → `Firing`)
6. 서비스 복구와 해제 통지 검증 (`[RESOLVED]`)
7. Grafana Cloud 원격 지표 시각화
8. 실습 스택 정리 (`docker compose down -v`)

### Grafana Cloud 무료 플랜

신용카드 등록 없이 이메일 인증만으로 즉시 시작하는 **영구 무료(Forever Free)** 플랜: 메트릭 10,000 시리즈, 로그·트레이스 각 월 50GB, 14일 데이터 보존, 최대 3명 활성 사용자.

### 부록 요약

- **하이브리드 관제 구조**: 사내망은 인바운드 포트(8080·9090 등)를 일절 열지 않고, 아웃바운드 HTTPS(443)로 Grafana Cloud의 Mimir(지표 수집기)에 TLS 암호화 푸시.
- **Alertmanager 고가용성(HA)**: 운영 환경에서는 단일 컨테이너가 아니라 3대 이상 노드를 Gossip 프로토콜로 클러스터링. 여러 Prometheus가 동일 경보를 중복 전송해도 클러스터 내부에서 중복 제거되어 수신자에게는 1건만 발송.
- **Webhook vs SMTP**: Webhook(HTTPS POST, 수십~수백ms, Slack/Teams 등 실시간 채널)과 SMTP(STARTTLS, 수 초~수 분, 운영 총괄·감사 이력 보존)를 상황에 맞게 분기. critical은 Webhook, 감사·보고용은 SMTP 병행이 실무 전략.
- **시계열 데이터 모델**: Counter(누적 카운터), Gauge(현재값), Histogram(버킷별 분포), Summary(사전 계산 분위수) 4종. 동일 메트릭 이름이라도 라벨 조합이 다르면 완전히 독립된 시계열로 저장됨.
- **JVM OOM 방지**: 컨테이너 `limits.memory`의 70~75%만 `-Xmx`로 배분(예: 512M 컨테이너 → 384M 힙). 1:1 매핑 시 OOM으로 강제 종료(Exit 137).
- **민감 자격 증명 관리**: Slack Webhook URL, SMTP 비밀번호, API 토큰을 소스코드/Git 저장소에 평문으로 커밋하지 않고 `.env` + `.gitignore`로 분리하거나, Vault·AWS Secrets Manager 등으로 런타임 주입.

## 2. 실습 중 실제로 다르게 됐던 부분 (틀린 점 위주)

### ① 비밀값을 `.env` 변수로 안 쓰고 하드코딩함

자료는 `${GRAFANA_CLOUD_REMOTE_WRITE_URL}`, `${GRAFANA_CLOUD_INSTANCE_ID}`, `${GRAFANA_CLOUD_API_KEY}`, `${SLACK_WEBHOOK_URL}`, `${GMAIL_APP_PASS}`처럼 환경변수로 치환하라고 명시합니다. 하지만 실제 `prometheus-cloud.yml`과 `alertmanager.yml`에는 Slack 웹훅 URL, Grafana Cloud 계정/비밀번호, Gmail 앱 비밀번호가 전부 파일에 **직접(평문)** 박혀 있었습니다. 부록의 "민감 자격 증명 관리 전략" 모범답변이 정확히 지적하는 문제로, Git에 커밋되면 그대로 노출됩니다.

### ② `receivers` 구조가 슬라이드가 경고한 그 실수 그대로였음

자료는 "보조 리시버는 기존 `receivers:` 목록에 이어 붙이되, 들여쓰기를 맞춰야 같은 목록의 항목으로 인식된다"고 명시합니다. 그런데 실제 `alertmanager.yml`은 `#  - name: 'email-notifications'`가 주석 처리된 채, `email_configs`가 `slack_configs`와 함께 **하나의 리시버(`notifications`) 안에** 합쳐져 있었습니다. 즉 원래 의도(심각도별 Slack/이메일 채널 분기)와 다르게, 지금은 모든 경보가 항상 Slack+이메일 둘 다로 나가는 구조입니다. `route`에도 `severity`별 분기 규칙이 없어, "labels.severity: 심각도별 라우팅 채널 분기"라는 자료 내용이 실제 설정에는 반영되지 않았습니다.

### ③ YAML 값에 따옴표를 안 씌워서 파싱 에러 발생

`smtp_auth_password` 값을 따옴표 없이 넣어 `did not find expected key` 에러가 발생했습니다. 자료가 "템플릿 변수가 쉘에서 치환되지 않도록 감싸서 작성"하라고 강조하는 것과 같은 원칙(설정값은 항상 안전하게 quoting)을 놓친 사례입니다.

### ④ `alert_rules.yml`이 파일이 아니라 디렉터리로 마운트됨

사전에 실제 파일을 준비하지 않고 compose를 먼저 띄운 전형적인 도커 바인드마운트 함정입니다. 자료에는 없는 내용이지만 실습 중 흔히 겪는 실수입니다.

### ⑤ `depends_on` 관계를 몰라서 반복적으로 포트 충돌 발생

자료의 예시 compose(17p)는 `app`이 다른 서비스의 의존성으로 걸려있지 않은데, 실제 프로젝트는 `alloy`/`prometheus`가 `app`에 `depends_on`을 걸어놔서, 인프라를 재기동할 때마다 IntelliJ 로컬 실행(8080 포트)과 충돌했습니다.

## 3. 핵심 기술 면접 질문 답변

### Q. Alertmanager의 그룹핑 기능이 없을 때 발생하는 경보 피로(Alert Fatigue)의 위험성은 무엇인가요?

핵심 DB나 스위치 장비처럼 여러 서비스가 공통으로 의존하는 인프라가 다운되면, 그 순간 의존하는 수십~수백 개의 서비스에서 동시에 개별 장애 경보가 쏟아집니다. 그룹핑 기능이 없다면 몇 분 만에 수백 건의 Slack 메시지가 발생하고, 운영자는 알림을 하나하나 확인할 수 없어 결국 채널을 음소거하게 됩니다. 문제는 이 음소거가 걸려있는 동안 정작 가장 치명적인 근본 원인 경보까지 함께 놓치게 된다는 점입니다 — 즉 경보 피로는 알림이 부족해서가 아니라 **과잉**해서 발생하고, 역설적으로 알림을 줄이려는 행동(음소거)이 가장 위험한 순간에 대응을 늦춥니다.

Alertmanager는 `route`의 `group_by`(예: `alertname`, `severity`)를 기준으로 같은 원인에서 발생한 개별 경보들을 하나의 그룹으로 묶어, `group_wait`(초기 병합 대기, 기본 10s) 동안 들어오는 관련 경보들을 모아 **단 1건의 통지**로 발송합니다. 이후 동일 그룹에 새 경보가 추가되면 `group_interval`(기본 1m) 주기로만 추가 통지하고, 미해결 상태가 계속되면 `repeat_interval`(예: 1h)마다만 재발송합니다. 여기에 더해 억제(Inhibition) 규칙으로 상위 인프라 장애 시 그에 종속된 하위 컨테이너들의 연쇄 경보를 아예 차단해, 운영자가 근본 원인 하나에만 집중할 수 있게 합니다.

결과적으로 그룹핑은 "얼마나 많은 서비스가 영향받았는가"를 하나의 신호로 압축해서, 알림 폭탄을 원천 방지하고 신뢰할 수 있는 경보 채널을 유지하는 역할을 합니다.
