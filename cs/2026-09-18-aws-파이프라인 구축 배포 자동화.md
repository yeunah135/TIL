# AWS EC2 Blue/Green CD 파이프라인 — 학습 정리

> 날짜: 2026-09-18

## 1. 수업 핵심 요약

### Continuous Delivery vs Continuous Deployment

| 구분 | Delivery | Deployment |
|---|---|---|
| 릴리스 | 수동 승인 게이트 필요 | 테스트 통과 시 완전 자동 |
| 채택 환경 | 금융·공공·의료 등 규제 도메인 | SaaS·스타트업 등 속도 우선 |

### 배포 아키텍처 (Push vs Pull)

- **Push (GitHub Actions SSH)**: 외부 러너가 SSH 22번으로 접속해 명령 전달 → 가시성 높음, 인바운드 포트 필요
- **Pull (Watchtower)**: 호스트 내부 상주 에이전트가 GHCR을 감시 → 포트 개방 불필요, 로그 가시성 낮음

### 단일 인스턴스 Blue/Green 무중단 배포 흐름

1. `service-url.inc` 한 줄로 현재 활성 서비스(blue/green) 판별
2. 비활성 서비스만 `pull` + `up -d`로 기동
3. 비활성 포트로 최대 10회(3초 간격) 헬스체크 → `200` 응답 확인
4. `service-url.inc` 갱신 + `nginx -s reload` (연결 끊김 없이 전환)
5. 구버전 `stop` + `docker image prune`으로 자원 회수

### 오늘 직접 구축한 파이프라인

```
Git Push → CI(ci.yml, 테스트 게이트) → CD(cd.yml, workflow_run 체이닝)
→ SSH 원격 접속(appleboy/ssh-action) → deploy.sh 실행
→ Nginx 무중단 전환 → Slack Webhook 알림
```

추가로 **Watchtower 폴링/웹훅 모드**를 임시 구동해 Pull 방식 동작을 검증한 뒤 다시 Push 파이프라인으로 복귀.

## 2. 오늘 겪은 문제와 원인 (트러블슈팅 정리)

| 증상 | 원인 | 해결 |
|---|---|---|
| `aws sts get-caller-identity` → NoCredentials | 자격 증명 미설정 (`aws login`은 실존 명령 아님) | `aws configure sso` 사용 |
| `aws configure sso` 실행 시 xterm-256color 에러 | Git Bash(mintty)가 Windows 콘솔이 아니라서 SSO 로그인 흐름과 충돌 | PowerShell/cmd.exe에서 실행 |
| `aws sts get-caller-identity --profile student10` 무응답 | SSO 프로필은 설정됐지만 실제 로그인(`aws sso login`)이 안 됨 | `aws sso login --profile student10` |
| `echo hello`조차 출력 안 됨 | AWS와 무관, **터미널(mintty) 자체가 먹통** (Ctrl+S 오정지 또는 세션 꼬임) | 터미널 재시작, 다음부터는 `Ctrl+Q` 먼저 시도 |
| `GetParameter ... ParameterNotFound` | SSM Public Parameter 경로의 `26.04`가 오타 가능성 (정식 LTS는 24.04 등) | `24.04` 경로로 재확인 필요 |
| `GetParametersByPath ValidationException` | **Git Bash의 자동 경로 변환(MSYS pathconv)**이 `/aws/...`를 Windows 경로로 오인 | `export MSYS_NO_PATHCONV=1` |
| SSH `Connection refused` (host 공백) | `$PUBLIC_IP` 변수가 비어있음 (export 안 됨) | `describe-instances`로 조회 후 `export PUBLIC_IP=...` |
| `curl <https://get.docker.com>` → No such file | `< >`를 bash가 **입력 리다이렉션**으로 해석 | 꺾쇠괄호 없이 URL만 입력 |
| `pbcopy < ./.pem` → No such file (반복) | EC2 서버 안에서 **로컬 변수(`$MY_KEY_NAME`)를 참조** — SSH 세션은 별개 셸이라 로컬 export 미전달 | 로컬 터미널로 돌아가서 실행 |
| `compose.yml`의 `app-blue`/`app-green` 이미지가 `ghcr.io/a1l1ke/260918_ci-cd:latest` (실습 템플릿 값 그대로) | CI가 실제로 push하는 이미지(`ghcr.io/yeunyeuna/260918_ci-cd`)와 다른 **강사 계정 이미지를 그대로 참조** — 커밋 diff에 원작자 경고 주석까지 있었음 | 두 `image:` 값을 본인 GHCR 경로(`ghcr.io/yeunyeuna/260918_ci-cd:latest`)로 수정 |
| `docker compose pull` → `unauthorized` | GHCR 패키지가 기본값 **private**이라 EC2가 인증 없이 pull 불가 (CI가 쓰는 `GITHUB_TOKEN`은 Actions 실행 중에만 유효해 EC2에서 재사용 불가) | GHCR 패키지 설정에서 **Visibility → Public** 전환 (private 유지하려면 EC2에서 `read:packages` 권한 PAT으로 `docker login ghcr.io`) |
| GitHub Actions CD 로그: `ssh.ParsePrivateKey: ssh: no key found` | `EC2_SSH_KEY` Secret 값이 비어있거나 `BEGIN/END PRIVATE KEY` 헤더 누락, 복사 중 개행 손상 등으로 **유효한 PEM이 아님** | `.pem` 파일 전체 내용(헤더~푸터 포함)을 그대로 복사해 Secret **재생성** 후 Actions에서 Re-run |
| `deploy.sh: service-url.inc: Is a directory` / nginx 로그 `pread() ... failed (21: Is a directory)`로 `nginx-proxy`가 계속 `Exited` | `nginx-proxy` 컨테이너가 **최초 기동 시점**에 호스트에 `~/service-url.inc` 파일이 없어 Docker가 그 경로에 빈 디렉토리를 자동 생성해 마운트함. 이후 파일을 정상 생성해도 **이미 떠 있던 컨테이너의 마운트는 그대로 유지**되어 나중엔 `sudo rmdir ~/service-url.inc`가 오히려 `Not a directory`로 실패(이미 파일이라는 뜻) | `rmdir`이 아니라 `sudo docker compose up -d --force-recreate nginx`로 **컨테이너 자체를 재생성**해야 새 마운트가 적용됨 |
| `git push` → `[rejected] (fetch first)` | 원격에 로컬에 없는 커밋 존재(예: GitHub 웹에서 직접 `index.html` 수정) → 로컬/원격 히스토리 분기 | `git pull --rebase origin main` → 충돌 파일 수동 병합(`<<<<<<<`/`=======`/`>>>>>>>` 마커 제거) → `git add` + `git rebase --continue` → 재푸시 |

**공통 패턴**: 오늘 문제는 크게 두 갈래였음. ① **Windows Git Bash 환경 특유의 함정**(경로 자동변환, 콘솔 비호환, 세션 간 변수 미공유, 리다이렉션 기호 오해), ② **CI/CD 설정값을 실습 템플릿 그대로 두고 넘어간 실수**(다른 계정 이미지 참조, private 패키지, 잘못된 Secret 값) — 둘 다 "로그를 끝까지 읽고 값이 정말 내 것으로 채워졌는지 확인"하면 예방 가능했던 문제들.

## 3. 면접 예상 질문 3개 + 답변

### Q1. Continuous Delivery와 Continuous Deployment를 가르는 기준은 무엇인가?

> 비즈니스 측면에서는 도메인의 규제 요구사항과 릴리스 실패 시 손실 규모가 기준입니다. 정기 점검 창이 필요하거나 이해관계자 사전 승인이 필수인 서비스는 수동 승인 게이트를 둔 Delivery를 채택합니다. 기술 측면에서는 테스트 자동화 신뢰도가 확보되고, 장애 시 수 초 내 롤백 가능한 헬스체크/롤백 인프라가 갖춰져 있다면 Deployment로 전환해 피드백 루프를 단축합니다.

### Q2. 단일 인스턴스 Blue/Green 배포에서 헬스체크와 자동 롤백이 왜 필수적인가?

> 프로세스가 떠 있다는 것만으로는 트래픽 처리 가능 상태를 보장하지 못합니다. DB 커넥션 지연, 환경변수 누락 등으로 프로세스는 살아있지만 500을 반환할 수 있기 때문입니다. 따라서 프록시 전환 전 신규 컨테이너 포트로 실제 HTTP 엔드포인트를 반복 폴링해 200을 확인하고, 실패 시 신규 컨테이너를 중단하고 기존 활성 상태를 유지하는 자동 롤백이 필요합니다.

### Q3. GitHub Actions에 SSH 프라이빗 키를 Secrets로 등록하는 방식의 취약점과 대안은?

> 키가 유출되면 EC2 관리 계정 권한이 그대로 탈취되며, Runner의 유동 IP를 수용하려고 22번 포트를 광범위하게 열어야 하는 부가 취약점도 생깁니다. 대안으로는 ① OIDC 연동으로 고정 키 없이 단기 IAM 임시 자격 증명 발급, ② 22번 포트를 닫고 AWS Systems Manager Session Manager로 명령 전달, ③ 프라이빗 서브넷에 Self-hosted Runner를 배치해 내부망 통신으로 배포하는 방법이 있습니다.
